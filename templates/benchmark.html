Key Architectural Finding

Defunct services built with client-side JavaScript routers, redirects, or Flash wrappers (such as Adobe Flash [3,696 chars], Yahoo Answers [3,220 chars vs 603 HTTP], GeoCities [1,721 chars], and Grooveshark [1,118 chars vs 223 HTTP]) yielded negligible text via plain HTTP. Browserbase headless browser execution is required to execute historical JS scripts and follow multi-hop Wayback redirects. Conversely, early Web 1.0/2.0 text portals (such as Digg [5,337 chars] and Picnik [790 chars]) exhumed with speed and fidelity over plain HTTP.

Case Study

The GeoCities Anomaly: Wayback 301 Redirects & Flash Containers

A real-world breakdown of why automated archival exhumation fails on basic crawlers, and how the cemetery’s guardrails prevent fabricated obituaries.

Exhumation Forensic Breakdown

Why GeoCities Triggered “Archival Evidence is Thin (<600 Chars Recovered)”

1. The Wayback 301 Redirect Trap

When exhuming http://geocities.com/ on January 3, 2007, the Wayback Machine returns an interstitial HTTP 301 redirecting to http://geocities.yahoo.com/. Plain HTTP crawlers stop at the redirect wrapper, recovering 0 to 50 characters of text.

2. Embedded Flash / Ruffle Containers

The historical Yahoo GeoCities portal loaded promotional subscription tiers inside Flash objects (emulated today via Ruffle). Without Chromium JavaScript execution, curl sees empty <div> tags without readable content.

3. Guardrail Badge & Honest Fact-Check

Because recovered text fell below 600 characters, the cemetery stamped GeoCities with the yellow badge: “Likely Cause of Death: Unknown · Archival evidence is thin”. Gemma verified 5 historical assertions, removing 0, refusing to hallucinate an ungrounded death narrative.
